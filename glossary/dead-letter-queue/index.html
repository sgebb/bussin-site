Dead-Letter Queues (DLQ)

In Azure Service Bus, a Dead-Letter Queue (DLQ) is not a separate queue. It is a secondary sub-queue automatically attached to every queue or topic subscription to isolate messages that cannot be processed or have expired.

Why Messages Get Dead-Lettered

The broker automatically moves messages to the DLQ when specific conditions are met, attaching two details: DeadLetterReason and DeadLetterErrorDescription.

  • MaxDeliveryCountExceeded: A consumer locked and abandoned a message more times than the queue's configured MaxDeliveryCount (default is 10). The broker moves it to prevent infinite retry loops.
  • TTLExpiredException: If EnableDeadLetteringOnMessageExpiration is turned on, messages that are not read before their Time-To-Live (TTL) expires are moved to the DLQ.
  • HeaderSizeExceeded: The total size of custom user headers exceeds protocol limits.

Topic Subscription Resubmission

A limitation of Azure Service Bus involves topic subscriptions:

Note: You cannot send a message directly into a specific subscription's active queue. To resubmit a dead-lettered message from a subscription's DLQ, you must send it back to the parent topic.

This means the resubmitted message will be evaluated against all active subscription filter rules on that topic, which can duplicate the message across other subscriptions. When running bulk replays in Bussin, keep this routing behavior in mind.

Sub-Queue Routing Paths

Because DLQs are sub-entities, clients address them using specific path decorators:

  • Queue DLQ: <queue-name>/$DeadLetterQueue
  • Topic Subscription DLQ: <topic-name>/subscriptions/<subscription-name>/$DeadLetterQueue

Bussin handles this path formatting automatically, opening connections to receive or purge your DLQ messages directly from your browser.
