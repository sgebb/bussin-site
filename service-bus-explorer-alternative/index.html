Service Bus tooling

Browser-native Azure Service Bus explorer alternative

Bussin.dev connects directly to Azure Service Bus using AMQP over WebSockets. It works in the browser, without Electron or a backend proxy, and is built for queue inspection, dead-letter recovery, and subscription troubleshooting.

Open demo — no login Open app

Why browser-native matters for Service Bus

  • No install, no desktop runtime: open the app directly in the browser and connect to namespaces from any operating system.
  • Direct AMQP over WebSockets: the client speaks the same protocol as managed Azure tooling, without proxying message traffic through a backend service.
  • Cross-platform compatibility: Mac, Linux, and Windows teams can use the same browser experience.

Typical workflows

Queue inspection

View queue metadata, live message counts, and lease state before you inspect or replay messages.

Dead-letter analysis

Browse dead-letter queues, inspect failure details, and move messages back into processing with confidence.

Topic subscriptions

Open subscriptions for direct message browsing and validate filter behavior without deploying code.

Consent and control

Bussin only operates when you explicitly tell it to. The full app requests Graph and Service Bus consent only to discover namespaces and issue direct Service Bus calls, and it cannot do anything autonomously.

For a quick preview, open the demo path without login or consent.

Limitations of desktop-only tooling

  • Electron and native apps require install, updates, and permission management.
  • Desktop tools often need a local proxy or VM network bridge for cloud AMQP.
  • Mac and Linux support can lag behind Windows-first clients.

Browser-native tooling removes those friction points and keeps the interaction directly in the browser.
